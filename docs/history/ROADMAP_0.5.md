## 1. 为什么是现在这条主线

0.4.9–0.4.13 五个版本都在打磨「记录得准不准、改错了能不能退」——这些做完了，产品现在是一台**准确的记录仪**：

- 记一餐要选食物、填份量、确认；记一次运动要填五个字段；体重可以改、可以作废、可以撤销。
- 但每天真正的问题是「今天还差多少、晚上吃什么、明天该买什么」，这些它一个都不回答。

所以下一阶段不是继续补记录功能，而是**让已有数据开始产出结论**。这也是原方案阶段 D 的位置——它一直没做。

## 2. 主线：动态菜单与补货

### 2.1 输入

| 数据 | 现状 | 缺什么 |
| --- | --- | --- |
| 菜谱（含食材与份量） | 有，但只有你自己建过的那几个 | **需要起步包** |
| 库存余量与到货时间 | 有（采购/制作/消耗完整） | 常有一段时间没更新 |
| 每日营养目标 | 有（热量/蛋白/纤维） | — |
| 周预算 | 有（采购记录可算） | — |
| 厨具与可用时间 | 无 | 先按菜谱自带的时长字段估 |

### 2.2 输出

**明日 3 餐候选**，每条必须带三样东西：

1. **一句理由**：补哪个缺口 / 消耗哪批临期 / 省多少钱；
2. **可核算的数字**：合计热量、蛋白、预计成本；
3. **可执行的动作**：「选它」→ 生成明日菜单；或「换一批」。

外加**补货清单**：只列"不足"和"未到货"的量，能一键变采购草稿（**不自动下单**）。

### 2.3 算法（确定性，四步，不接 AI）

```
1. 缺口 = 目标 − 近 7 天均值（热量、蛋白）
2. 候选 = 菜谱 × 可用库存（主料齐 ≥ 80% 才入选）
3. 排序 = 采购增量最小 → 临期主料优先 → 成本最低
4. 取 top 3，为每条生成一句理由（模板 + 实际数字，不编造）
```

**为什么不用 AI**：理由必须可追溯（"为什么推这道"要能指到具体库存与缺口），且必须离线可用、结果可复现。AI 放在 M4 之后再谈。

### 2.4 验收

- 任选一天，能给出 3 个候选，每条理由都能追到具体数据；
- 「选它」生成的明日菜单与候选数字一致；
- 补货清单里的量 = 菜单所需 − 现有 − 在途；
- 断网、无菜谱、无库存三种情况都有明确空态，不崩不瞎猜；
- 不改动任何历史记录。

### 2.5 不做

自动下单、真实 AI 推荐、跨设备同步、营养医学建议。

## 3. 起步包（主线的数据前提）

`design/starter-pack.json`（M3 产出）：

- 你的标准锅（里脊 400 g + 北豆腐 300 g + 白菜 400 g + 洋葱 100 g + 油 10 g）与米饭换算；
- 常用食材 8–12 个（含营养与常见包装规格）；
- 早餐固定组合（燕麦 / 酸奶 / 莓果 / 全蛋）。

规则：

- 走**正常领域命令**创建，因此导入后可以照常编辑、作废；
- 只在「菜谱列表为空」时提供入口，避免覆盖已有数据；
- 导入前展示将创建的内容清单，导入后写审计事件 `starter_pack_imported`。

## 6. 风险与对策

| 风险 | 会怎么坏 | 对策 |
| --- | --- | --- |
| 起步包被当成"系统预置" | 以后改不动 | 走正常命令创建，可编辑可作废，并在导入后提示"这些是你自己的数据" |
| 库存长期不更新 | 菜单推荐用过期库存 | 菜单卡上标"库存最后更新于 N 天前"，超 5 天先提示盘点 |
| 迁移期两套样式并存 | 页面新旧混杂 | 按页迁移，每页迁完即删旧规则；守卫在 M2 结束才允许全绿 |
| 搬家后路径失效 | 构建/文档指向旧地址 | 搬家后立刻重建 + 全仓 grep 旧路径 |
| 设计文档腐化 | 三个月后没人看 | 文档只写规则不抄数值；数值只在 tokens.css |

## 7. 明确不做（0.5 期间）

- 手机端、响应式重排（只保证 1366 不碎）。
- 新依赖（Tailwind / Radix / 组件库），只移除无用的 `react-router-dom`。
- 深色主题（M4）。
- 数据迁移、数据库结构变更（M1.5–M3 全部零迁移）。
- 自动下单、账号体系、云同步。
