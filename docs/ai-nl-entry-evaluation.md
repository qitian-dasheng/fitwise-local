# AI 自然语言饮食录入评估报告（第一阶段交付物）

> 评估日期：2026-10-22 ｜ 环境：Ollama 0.40.7 · RTX 3060 Laptop 6GB · 本机已有模型（零下载）
> 性质：纯评估，未修改任何业务代码。本报告区分【实测】与【推测】，结论供裁决，不代表已确认决定。

## 1. 评估问题

用户假设："自然语言饮食录入"是 AI 唯一可能值得保留的能力。需要验证：
中文理解与食物/数量识别准确率、与现有食物库的匹配、性能（延迟/显存/按需加载）、纠错成本、集成难度。

## 2. 关键发现：思考模式是性能元凶（实测）

| 配置 | 单句耗时 | 输出 token | 格式正确率 |
| --- | --- | --- | --- |
| qwen3.5-4b 思考模式开（默认）【实测 8 句】 | 16–102 秒 | 1200+ | 7/8（1 句超时异常） |
| qwen3.5-4b `think:false` + num_predict 256【实测 6 句】 | **0.7–1.7 秒** | 35–114 | **6/6** |

推理速度本身约 74 token/s（GPU 正常），慢的全部原因是 qwen3.5 默认生成大量内部思考痕迹。
关闭后**提速 25–60 倍**，进入"日常可用"区间。

## 3. 识别质量【实测，人工逐条核对】

v3 六句全部通过（模型已卸载，原始数据在 build-logs/ai-eval/results_v3_thinkoff.jsonl）：

| 句子 | 识别结果 | 人工核对 |
| --- | --- | --- |
| 早上吃了一碗燕麦粥，加了一杯酸奶和一些蓝莓 | 粥/酸奶/蓝莓 3 项，量词正确解析 | ✓ 蓝莓"一些"给了合理估算 40kcal |
| 中午标准锅炖了里脊豆腐白菜，我吃了一半锅 | **拆成里脊/豆腐/白菜 3 组分**，"半锅"理解正确 | ✓ 结构理解惊艳；营养合计偏保守（约 185 vs 实际约 500 kcal），量级正确 |
| 100克燕麦片 | 100g/370kcal/13g 蛋白 | ✓ 与食物库标注 417kcal 差 11%，同量级 |
| 一小把莓果大概80克 | 80g；热量/蛋白诚实填 null | ✓ 不编造（prompt 规则生效；可回退食物库查莓果数据） |
| 两个鸡蛋一颗苹果 | 双食物双数量 100g/140kcal + 150g/95kcal | ✓ 与标准值一致 |
| 猪里脊200克煎着吃了 | 200g/350kcal/26g 蛋白 | ✓ 与生里脊标准值差约 13%，同量级 |

- 中文理解/数量识别：**6/6 正确**（含量词变体"颗→个"、做法词"煎"、轻衡口径"半锅"）
- 与食物库匹配：食物库仅 8 条（4 条点验残留）且你日常"直接记餐"，**匹配库不是价值点**；NLU 的价值在直接给出估算建议
- 纠错成本：估算偏差实测在 ±30% 内，且按红线设计所有 AI 值仅作建议、逐项人工确认后入库，纠错=改个数字

## 5. 集成架构草案（若你批准实施，另立轮次）

- 调用：Tauri 前端 fetch `http://localhost:11434/api/generate`，**零新增 Rust 依赖**；要求本机运行 Ollama
- 交互：饮食页一个输入框 → AI 返回建议项（标记"AI 估算"）→ 逐项人工确认/修改 → 确认后才写入（红线：永不静默入库）
- 参数：`think:false` + `num_predict:256` + `format:json` + `temperature:0.1`；`keep_alive` 按需（单条用完即卸，批量录入保持）
- 失败降级：Ollama 未运行/超时 → 回退现有手工表单，核心功能零依赖 AI
- 维护成本：prompt 约 15 行（已验证）+ 模型升级时重跑 6 句回归（脚本已留存 build-logs/ai-eval/）

## 6. 维护成本与风险【推测为主】

- Ollama 服务需在运行；未运行时功能不可用（有降级，无损失）
- 模型文件 3.3GB 磁盘占用（已存在）
- qwen3.5 默认思考模式行为可能随模型版本变化——prompt 与参数需随版本回归（脚本可复用）
- 隐私：句子仅发往本机模型，不出网

## 7. 结论（供裁决）

自然语言录入在"关思考"配置下满足日常使用要求：**识别 6/6 正确、单句约 1 秒、零费用、全离线、纠错成本低**。
实测与推测的边界：6 句样本小（推测：更复杂句式/口语化输入的准确率会下降）；营养估算只是建议（推测：长期使用中 AI 估算与食物库精确值的差距需要人工修正约 1–2 成条目）。
